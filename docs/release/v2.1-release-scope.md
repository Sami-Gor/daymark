# Daymark V2.1 — owner-approved release scope

**Decision recorded:** 2026-11-06  
**Decision status:** Product scope approved by the owner; implementation and release validation are not complete.  
**Release status:** NOT READY. This document records the target, not a claim that the functionality is currently implemented or production-ready.

## 1. Approved product scope

V2.1 is intended to provide fully on-device, offline voice input and narration in English, French and Spanish.

| App language | Ask Daymark (speech recognition) | Hear today (narration) |
|---|---|---|
| English | Required | Required |
| French | Required | Required |
| Spanish | Required | Required |

All six combinations are release acceptance requirements. V2.1 must not ship as a partial multilingual release: all six combinations must pass physical-device acceptance before release.

### Language selection

- The selected Daymark interface language is the single language selection for both Ask Daymark and Hear today.
- No independent voice-input language selector is planned.
- Ask Daymark must use the recognition model for the selected app language.
- Hear today must use the corresponding language's narration voice.

### Offline and fallback policy

- Recognition and narration must run locally after the required language pack is installed.
- No cloud speech recognition, cloud TTS, Android system speech recognition or Android system TTS fallback is permitted.
- A language/model failure must not silently switch languages or services.
- Weather and text functionality must remain usable when voice functionality is unavailable.

## 2. Language-pack delivery and management

### Initial installation

- English recognition and narration are available from the initial app installation.
- English is the default/preinstalled language and cannot be removed by the user.
- French and Spanish are optional downloads.

### Pack composition

Each optional language is one combined pack containing both:
1. The offline speech-recognition model for Ask Daymark.
2. The offline narration model/voice for Hear today.

The user sees one installed status, one download action and one removal action per optional language.

### Download behaviour

- Selecting a language whose pack is not installed prompts the user before downloading.
- The current language remains active until the new pack is downloaded, verified and installed.
- Show the download size before confirmation.
- Allow downloads over Wi-Fi or mobile data, with explicit user confirmation.
- Check available storage before starting. The check must account for download and installation/staging requirements, not just the compressed download size.
- Do not automatically delete another language pack to make room.
- Pack transport must use HTTPS.
- Each pack must be versioned and integrity-verified (SHA-256 or an equivalently strong, documented integrity mechanism) before it becomes active.

### Removal and updates

- Settings must show installed optional languages and their storage sizes.
- Users can remove and later reinstall French and Spanish.
- English cannot be removed.
- When a newer optional pack is available, notify the user and ask before downloading it.
- Keep the existing working pack active while an update downloads.
- Verify the replacement before activation. Do not remove the existing working pack until the replacement is successfully installed and verified.

### Failure behaviour

If a language pack fails to download, install or load:
- Show a clear, translated error.
- Offer retry and removal/cleanup of incomplete downloaded data.
- Preserve any previously working version and all other installed language packs.
- Do not fall back to English automatically, cloud services or Android system speech.
- Keep weather and text-based functionality usable.

### Delivery architecture

**TBD — not selected.** The hosting/delivery architecture is intentionally undecided. The implementation must satisfy the HTTPS, versioning, confirmation, integrity, storage, update and offline requirements above. Do not assume that the current install-time Play Asset Delivery setup is the approved final architecture.

## 3. Platform compatibility

- Minimum supported Android version remains **Android 10 / API 29**.
- The multilingual voice scope must not raise the app's minimum Android version.
- Device capability and model-resource requirements must be validated across the supported range. A device that meets the Android API minimum must not be assumed to have adequate memory, storage or inference performance without evidence.

## 4. Physical-device acceptance gate

Before V2.1 release, all six combinations must pass on physical Android hardware:

| Test area | English ASR/TTS | French ASR/TTS | Spanish ASR/TTS |
|---|---:|---:|---:|
| Recognition quality and expected language | Required | Required | Required |
| Narration intelligibility and correct language/voice | Required | Required | Required |
| Operation with network unavailable after installation | Required | Required | Required |
| Pack download, integrity check and installation | Preinstalled baseline | Required | Required |
| Missing/corrupt/incomplete pack failure UX | Required | Required | Required |
| Stop/cancel, lifecycle and recovery | Required | Required | Required |
| Pack update preserves previous working version | Baseline | Required | Required |
| Remove and reinstall optional pack | Not applicable | Required | Required |

Physical-device evidence must identify the model, OS/API level, app commit/build, model/pack versions, network state, test procedure and result. Host benchmarks and JVM tests are supporting evidence only; they do not satisfy this gate.

## 5. Current implementation gap assessment (branch head fa650be)

The following is a source-level assessment of the current `poc/multilingual-android-tts` branch. It is not a device-validation result.

| Area | Current branch evidence | Gap against approved V2.1 scope |
|---|---|---|
| Narration | Kokoro routes English, French (`ff_siwis`) and Spanish (`em_alex`) in the debug POC. | `daymark-voice/build.gradle` sets `MULTILINGUAL_NARRATION=false` for release. The app build also explicitly rejects French/Spanish voice files in release assets. Production multilingual narration is not enabled. |
| Recognition | The native Android plugin builds one Parakeet TDT 0.6B v3 int8 recogniser from one fixed model asset set. The JS bridge passes a `lang` value, but the current native `start(PluginCall)` path does not select a model from that value. | French and Spanish recognition model selection/integration is not implemented in this branch. UI-language-following recognition is not yet achieved by the native implementation. |
| English model delivery | The current Parakeet asset pack is an install-time Play Asset Delivery pack. The current model files are approximately 640 MB uncompressed. | The approved target requires English preinstalled, but French and Spanish as separate user-initiated optional packs. The existing install-time single-model delivery arrangement is not the approved complete pack-management design. |
| French/Spanish packs | The Kokoro fetch script stages French/Spanish voices in debug assets. | No complete combined ASR+TTS optional pack lifecycle is established: model choice, manifest/versioning, hosted download, progress, consent, storage preflight, integrity, atomic activation, update, removal and reinstall remain to be implemented. |
| Offline and failure policy | Existing voice paths are designed to fail rather than use system/cloud fallbacks. | Extend and verify that policy for downloadable French/Spanish packs and every pack lifecycle failure state. |
| Android floor | `variables.gradle` sets `minSdkVersion = 29`. | Preserve API 29 and validate the new language-pack and multilingual inference paths against that floor. |

### Specific technical decisions still required

1. Select and evaluate suitable French and Spanish **offline ASR models**. The current Parakeet TDT 0.6B v3 assets are one fixed recogniser; the multilingual TTS work does not provide multilingual ASR.
2. Confirm licensing, redistribution, provenance, size, supported architectures and runtime compatibility for each selected ASR model and every pack component.
3. Define a versioned pack manifest and safe installer/activation lifecycle.
4. Choose the HTTPS hosting and delivery architecture (still TBD).
5. Implement the user-facing language-pack settings and download/update/removal states.
6. Enable production French/Spanish narration only after its assets, licence notices, integrity checks and production packaging are verified.

## 6. Other release gates remain separate

This scope decision does not close or waive:
- Physical-device testing of all six voice combinations and broader lifecycle/OEM compatibility.
- The independent security review and disposition of its findings.
- The known non-audio functional issues previously tracked as D1 (offline weather cache), D2 (manual town persistence), D3 (Location Services error copy) and the D4 refresh-control scope decision.
- The known `:daymark-voice:lintDebug` MissingPermission finding, which must be fixed or explicitly accepted and documented.
- Production-signed AAB generation and verification, Play Console declarations, release notes and final release approval.
