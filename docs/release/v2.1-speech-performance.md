# V2.1 speech performance and long-utterance evidence

**Status:** host benchmark measured; Android performance and playback latency are
**not verified**. This document records host CPU evidence only. It does not
establish phone memory, thermal, AudioTrack or airplane-mode behaviour.

## 1. Canonical corpus

The tracked corpus is `benchmarks/tts/corpus/{en,fr,es}/{25,100,250,500}.txt`.
The manifest pins the raw/normalized counts, hashes, expected segment counts,
voice, locale, date-format context, and G2P/PUA/runtime versions. The runner
validates those values before synthesis and checks that segments concatenate
to the exact normalized text.

The 500-word fixtures are exactly 500 raw words. Normalized counts are English
500, French 507 and Spanish 509 because the language-specific number/unit
normalizer expands some tokens.

## 2. Host baseline

The latest verified full run was produced on a darwin/arm64 host with Node
26.8.2, using the pinned 92 MB quantized Kokoro model and the three selected
voices. All 12 fixtures passed validation.

Warm 500-word wall times were 130,997 ms (English), 112,504 ms (French) and
112,801 ms (Spanish). The cold initialization range was approximately
1.35–1.46 s. Peak RSS ranged from approximately 327 MB to 559 MB. Two-run
reproducibility for the 500-word cases was within 0.4%.

Those wall times come from two different harness paths. English streams segment
by segment. French and Spanish phonemize and synthesize **one segment at a
time** in a host loop and concatenate the result (see §5). The app instead makes
one whole-text `nativeSynth` call for French and Spanish. The French/Spanish
wall times above therefore do not estimate the app's narration time, its
first-audio delay, or its stop behaviour.

The runner records **time to first generated segment** in
`RUN.firstAudioMs`. It is host generation time from the start of a repetition,
after model initialization, to the first segment's samples. It excludes model
loading, asset copying, JNI marshalling, `AudioTrack` creation and start, audio
focus and buffer filling. It is not Android playback latency and is not a
substitute for time-to-first-audio measured from a tap on a phone.

The comparison is also not like-for-like across languages. For English the
benchmark's first segment approximates what the app can stream first. For
French and Spanish the benchmark's first segment is synthesized and returned
immediately, while the app cannot play any audio until the entire utterance has
been phonemized and synthesized. The benchmark's French/Spanish
`firstAudioMs` must not be compared with French/Spanish app time-to-first-audio,
and it does not show that the provisional first-audio target is met.

## 3. Component metrics

`results.json` records, per run and per segment:

- total wall time and output sample count;
- G2P time, tokenization time and acoustic synthesis time;
- IPA character count and token count;
- unknown phoneme and PUA counts;
- finite-audio, peak, average and final-segment checks;
- process RSS samples;
- cold init time, warm repeats and separately labelled artificial delays.

Audio playback time is not measured by the host harness. The Android
`AudioTrack` path and real device time-to-first-audio remain a device test.

## 4. Long-utterance findings

The corpus and runner cover multiple sentences, long sentences, repeated
phrases, French/Spanish accents, numbers, dates, times, decimals, weather
units, punctuation and segmentation. The 12-fixture run had no truncated
output, missing segment, empty audio, unknown phoneme/PUA token or incomplete
final segment. Segment reconstruction is checked before synthesis.

No unbounded host memory growth was observed in the bounded repeated runs.
Cancellation responsiveness and overlapping playback cannot be established by
the host synthesis harness; they are covered by deterministic JVM state tests
and still need device playback validation.

## 5. Synthesis path implemented on Android

English uses the native stream: `KokoroLocalTtsEngine` calls
`nativeStreamStart`, pushes the segment plan with `nativeStreamPush`, and the
playback loop writes each `nativeStreamNext` chunk to `AudioTrack`. The native
stream uses the English Misaki G2P.

French and Spanish do **not** use segment-level prephonemized synthesis in the
app. `KokoroLocalTtsEngine.synthesizeAndPlay()` attempts the same stream start,
but `nativeStreamStart` rejects every non-English locale with
`"prephonemized stream not available"`. The Java layer then calls
`nativeSynth(text, lang, voice)` **once with the entire utterance**. The JNI
function phonemizes that whole text with `piper-plus-g2p` and calls
`synth_phonemes` once; only after it returns does `playSamples()` create the
`AudioTrack` and start playback. An optional segment plan is not used for
French/Spanish synthesis: the fallback receives the unsegmented `text`.

The benchmark's French/Spanish `monolithic` mode is a third path: it phonemizes
and synthesizes each segment separately in the host harness. That harness is
what produces the per-segment French/Spanish timings in §2; it is not the
Android implementation. In particular, the harness can produce a short first
segment's audio long before the app can produce any French/Spanish audio.

A streaming redesign was **not implemented**. The existing host baseline does
not demonstrate that a new French/Spanish streaming architecture would reduce
end-to-end latency enough to justify changing phoneme boundaries or the
validated synthesis path. The present design preserves exact normalized text,
segment ordering and voice selection.

### Unresolved device risks

These follow from the implemented path. They are not device measurements and
must be checked on hardware:

- **Delayed first audio for French and Spanish.** No audio is written until the
  whole-utterance `nativeSynth` call returns and the JNI float array has crossed
  back into Java. The host 500-word warm totals were about 112 s for each
  language on the benchmark's per-segment path; the app's whole-text call is a
  different workload and will differ on a phone, but the app still cannot start
  playback before that call completes. The provisional "cold ≤ 5 s" first-audio
  gate is defined for the English stream only; it does not apply to this path,
  and there is no French/Spanish first-audio evidence.
- **In-flight native synthesis cannot be cancelled.** `stop()` invalidates the
  playback generation and pauses/flushes an existing `AudioTrack`, but a
  `nativeSynth` call already running on the worker has no cancellation handle.
  The generation is only re-checked after `nativeSynth` returns, so a stop
  during French/Spanish synthesis does not interrupt the native work. A
  following `speak()` is posted to the same single worker and waits behind it.
  Stop returns to the caller, but CPU, memory and worker occupancy continue
  until synthesis finishes.
- **English cancellation is item-bounded, not instant.** The English stream can
  observe a stop between `nativeStreamNext` items and between `AudioTrack`
  writes, but a native call already in progress still has to return first. The
  blocked interval is bounded by one stream item rather than a whole utterance.

The AudioTrack lifecycle, stop responsiveness and overlapping-playback
behaviour remain device tests. The deterministic JVM state tests cover the
bookkeeping, not the native call or audible latency.

## 6. Provisional Android targets

These are candidate gates for future device measurement, not accepted results:

| Gate | Provisional target |
|---|---|
| Cold model initialization | ≤ 4 s on a supported arm64 phone |
| Time to first audible audio, cold, English stream | ≤ 5 s |
| Time to first audible audio, cold, French/Spanish whole-text | Measure per language; the English target does not apply |
| Warm synthesis RTF | < 1.0 on the target phone |
| Peak process RSS during 500-word narration | Establish per-device baseline; investigate above 800 MB |
| Long-utterance stop responsiveness | Stop returns to idle within 250 ms; native work must also stop (see §5) |

The targets must be revised after real device runs. No threshold is applied by
the benchmark runner, and this document does not claim Android readiness. The
stop target needs a measured distinction between the API returning and native
synthesis actually stopping; only the former is implied by the source.
